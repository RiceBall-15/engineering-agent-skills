# C4 架构约束

适用于系统上下文、容器、组件、部署和动态图。C4 是架构可视化方法，官方不强制形状或配色；本技能把其表达与审查建议作为默认验收要求。来源见文末。

## A1：固定主体范围与抽象层级

| 图种 | 主体与允许内容 | 禁止的混淆 |
| --- | --- | --- |
| C1 系统上下文 | 一个目标软件系统，以及直接相关的人和外部系统 | 不把内部 Controller、表或部署 Pod 与整个系统平铺 |
| C2 容器 | 一个系统内的应用、运行服务及数据存储；相关用户/外部系统作为支撑 | 容器指应用或数据存储，不专指 Docker；不列内部函数或实例副本 |
| C3 组件 | 一个容器内有职责的组件；相关外部容器、系统或用户作为支撑 | 不把整个系统拆解与某个容器内部组件拆解混为同级 |
| 部署 | 标明环境，展示部署节点及系统/容器实例，可嵌套基础设施边界 | 不把逻辑容器与具体实例视作同一对象；不编造副本数或可用区 |
| 动态 | 一个用例；复用静态模型对象，以编号表达交互次序 | 不把静态依赖当成已发生的调用；不把编号误当性能耗时 |

“同一层级”约束主体分解，不禁止 C2/C3 中出现必要的外部支撑元素。支撑元素须标类型与边界，不能伪装成内部同级组件。

## A2：每个节点有可识别的身份和职责

本技能采用以下文字模板；括号样式属于团队约定，信息字段来自 C4 表达建议：

```text
订单 API
[容器：Java / Spring Boot]
校验订单并协调创建流程
```

- 所有元素：名称、类型、简短职责。C2 容器及 C3 组件再标主要技术；未知写“技术待确认”，不得猜测。
- 人：角色名和使用目的。外部系统：名称、类型、与本图相关的职责；不展开无关内部实现。
- 数据存储：名称、存储类型/技术及保存什么。数据库、缓存、队列使用文字区分，不能只靠圆柱体图标。
- 边界框标所包含的系统/容器/环境名称；分组不能暗示不存在的网络隔离、事务或部署关系。

## A3：每条关系有方向和业务含义

- 使用单向箭头，标签说明源如何使用目标。双方分别发起有意义的交互时用两条边；不靠一条双向线隐藏不同含义。
- 容器间跨进程交互标协议或通信机制；组件内调用不编造 HTTP。概览 C1 不强行添加实现协议。
- 避免只有“调用”“使用”的空泛标签。优先写“提交订单 [HTTPS/JSON]”“发布订单已创建事件 [Kafka]”“读写订单 [SQL/JDBC]”；这些仅为示例，实际以证据为准。
- 箭头表示调用/依赖还是数据传递必须明确。例如“API 查询存储”的调用方向为 API→存储；若画返回数据，单独注明其不同方向和含义。
- 异步关系直接写“发布/消费事件”和机制；重试、幂等、事务边界若影响图意应有据可查。未确认关系在边上写“待确认”，不复用其他线型偷偷编码。

## A4：图面必须可以独立阅读

图头包含主题、图种/层级、主体范围和现状/目标/示意状态。部署图加环境；动态图加用例。提供图例，说明元素类型、边界和实际使用的线型/颜色。跨图命名、类型和颜色保持一致。

现状图依托代码/配置证据；目标方案明确标注提议。一个未经证实的缓存不能因为“常见架构都会有”而出现。C2 中展示订单 API、订单存储及已确认消息系统即可；内部校验器移到 C3，副本实例移到部署图。

## 架构图自检例

| 发现 | 判定与修正 |
| --- | --- |
| C2 中订单系统、validate()、数据库、Pod 并排 | 主体层级混乱；重新确定一个系统边界，函数与实例移到对应细节图 |
| C3 边界外出现支付系统 | 可以保留，标明外部系统；不要为“统一层级”删除必要上下文 |
| 连线仅写“调用” | 补业务动作；跨进程容器关系再补实际协议，未知项显式标记 |
| 目标图与现状图同名无状态 | 图头标明版本与状态，证据说明区分已实现和计划 |
| 技术未知，节点写成 Redis | 删除猜测；标明存储职责及待确认技术 |
