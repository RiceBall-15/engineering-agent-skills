# 开发全生命周期协作规约

面向团队共享的编程 Skill，适用于前端、后端、客户端、脚本、数据处理和基础设施代码。版本：1.3；整理日期：2026-10-15。

核心选择是**按风险分级，关键歧义才询问**。小改动直接推进；会影响业务含义、分支归属、兼容性、权限或真实数据的缺口必须先澄清。它提供可执行的协作约束，不代替团队已有工程标准与代码审查。

## 直接开始使用

将整个 `development-lifecycle` 目录放入所用工具支持的技能目录，保留 `SKILL.md` 与 `references/` 的相对位置。不要只复制主文件后丢掉其引用。

Codex 可使用其配置的用户技能目录，通常为 `$CODEX_HOME/skills`，未设置时为 `~/.codex/skills`。其他工具按自身技能加载方式放置；`agents/openai.yaml` 是可选的 Codex 展示元数据，正文不依赖它。此共享包没有安装脚本、hook 或自动 Git 操作，不会自行修改全局配置。

加载后可直接说：

```text
请使用 $development-lifecycle 完成这个需求：……
先检查仓库和会话分支，核对需求与已有实现；关键歧义才问我。
```

自动触发取决于宿主是否发现并加载本技能；不能仅凭文件已放置就断言已生效。首次使用让 agent 说明已加载的技能，并核对开工检查是否执行。跨聊天的分支归属与纠正需要持久化任务记录或规则，技能本身不会自动获得历史会话记忆。

如果工具只支持规则文件，可在项目现有规则入口引用此技能的路径，要求“开发类任务先读取该文件及当前操作需要的参考文档”；先验证该工具是否会解析该入口。避免把所有参考文档全文复制进全局提示词。

## 可直接转发给 agent 的安装指令

将 `development-lifecycle-v1.3.zip` 和下面这段话一起发给自己的 agent：

```text
请帮我安装附件中的 development-lifecycle 编程技能，并验证它可以加载和使用。

1. 先读取附件 README.md，确认当前工具实际支持的技能目录。我授权你将完整技能包安装到该目录，保留 SKILL.md、references/ 和其他配套文件的相对结构，不要多嵌套一层同名目录。
2. 如果已有同名技能，先比较并备份到技能发现目录之外，再更新；保留本地定制及 preferences.local.md，有冲突时向我说明。不要覆盖项目原有 AGENTS.md、CLAUDE.md 或其他开发规约。共享包不应包含作者的个人偏好文件。
3. 该技能不需要额外运行时。不要顺手安装 CodeGraph、ponytail 或其他插件，不要修改业务代码、切换 Git 分支、创建 worktree、提交或推送。
4. 安装后检查文件与内部引用是否完整，实际读取 SKILL.md 及 Git/worktree 细则。说明正确安装路径、版本和加载结果；如需我重新加载工具或开启新聊天，请给出操作方式，不要把复制成功说成自动触发已验证。
5. 做一次只读规则演练：解释“继续旧需求但当前目录在另一分支”“新需求基线不明确”“按项目策略将源分支合入目标分支”这三个场景应如何处理，不执行真实 Git 变更。

后续开发请按此技能先确认需求、项目规约和会话分支，优先复用已有能力，关键歧义才询问，并完成相应测试和交付记录。跨聊天需要依赖可读取的任务记录，不能假设已经记住所有历史。
```

上述指令授权接收它的 agent 安装本技能，仍需遵守宿主权限。如果工具不支持原生技能加载，agent 应说明可用的规则接入方式；需要修改项目规则文件时先给出具体方案，不直接覆盖。

安装验证只证明文件完整和规则可读取；三个场景是规则演练，不等于真实开发行为测试。正式首次使用时，可在一个明确的小需求中观察是否执行开工检查、使用正确分支并提供有效验证证据。

## 安装后首次使用

```text
请使用 $development-lifecycle 处理这个需求：<填写需求与材料位置>。
先检查当前项目规约、仓库状态和本会话对应分支，说明你理解的目标与验收方式。
关键歧义先问；普通实现细节按项目惯例处理。未经授权不要推送、合并或发布。
```

用户已经明确给过的授权持续有效；首次使用示例不要求对已授权动作重新确认。

## 个人约定与团队规则分开

个人长期约定可保存在宿主记忆，或技能安装目录的 `preferences.local.md`；主技能会读取其适用范围。更新保留、分享排除，不将个人偏好强加给同事。项目规则与个人规则发生实质冲突时先按优先级和适用范围判断，仍不明确时询问，不默默覆盖。

分支模型、测试交付、注释语言和工具链由各项目组决定；共享包不附作者的具体个人约定。进入新项目重新核对规则，不能自动沿用上一项目的例外。详见 [团队策略适配](references/team-policy.md)。

## 哪些返工经验被转成了规则

以下是对需求回顾的匿名化提炼，不包含原项目地址、账号、代码片段或内部配置：

| 已发生的问题 | 本技能的纠偏措施 |
| --- | --- |
| 按技术方案不断实现，却没有回到已确认需求核对 | 结合任务适用的需求、协议、原型或复现依据，按验收场景核对 |
| 重建已有工具与组件已能完成的能力 | 先列复用入口及限制，明确前后端职责，再决定新增实现 |
| 分支起点正确，后续却引入未经确认的其他需求 | 记录基线与依赖，按团队策略审查历史；明确每次同步的源 → 目标 |
| 延续聊天时在另一个需求分支修改 | 会话绑定仓库、分支、worktree；写入前恢复并核实 |
| 产品关键词导致反复选错技能 | 按动作与交付物路由；用户排除项持久化并传给子任务 |
| 新规范只改了代码，调用方和文档没跟上 | 契约、消费者、测试、说明纳入同一改动闭环 |
| 迁移步骤耦合，恢复边界不清 | 提取/备份/应用/核验/恢复各自明确，验证重试和并发编辑 |
| 编译或大量 mock 测试通过，却未证明实际行为 | 区分编译、单元测试、真实集成和产品验收证据 |

接口形式、注释格式、模型选择、运行时和数据保护机制遵循各项目的有效规约；历史做法只能作为理解上下文的证据，不能自动推广为公司标准。

## 与 ponytail 的结合

参考了 [ponytail 中文说明](https://github.com/DietrichGebert/ponytail/blob/main/i18n/README.zh-CN.md) 和 [其技能原文](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md)：先理解影响面，优先复用，以最少新增实现完成整个需求，保留必要校验、错误处理、安全和验证。

本包独立编写，不要求同时安装 ponytail；没有复制其整套提示词、品牌语气或性能数字，也不把“一行实现”“极少测试”作为指标。用户明确要求的功能和团队测试门禁优先，简洁不能成为漏做的理由。

Git 操作依据还核对了 [官方 worktree 文档](https://git-scm.com/docs/git-worktree) 与 [官方 merge 文档](https://git-scm.com/docs/git-merge)。分支保护、授权和团队集成策略仍由具体项目决定。

## 团队落地建议

先在一个小功能和一个跨模块需求中试用，再根据实际偏差微调。优先观察：是否问到了关键问题、是否改对分支、是否复用了现有能力、子任务是否越界、验证是否对应业务行为、提交是否混入无关内容。

通用原则维护在本技能；技术栈/接口/注释规范维护在项目规则；一次需求的分支与进度维护在任务记录。修订时记录触发问题与适用边界，不因为一次例外不断扩大全公司的强制流程。

本版已做结构校验和场景规则走查，具体范围见场景验收记录；尚未通过多个真实项目长期运行验证，不应把提示词约束当成强制执行的 Git 或 CI 门禁。

## v1.3 更新：面向多语言、多项目组

移除固定集成分支及反向同步禁令，改为依照团队策略和具体授权；支持功能分支、主干开发、发布修复和依赖分支。移除共享文档中作者个人测试交付策略的专门说明，改为读取项目的测试/CI 规则。

增加团队策略适配表，明确需求可以来自 Issue、协议、复现或设计决定，不要求所有任务都有 PRD/原型；验证方式、注释和工具选择按模块与语言适配。个人文件仍只留在本地，正式共享包按审核后的文件清单打包。

## v1.2 更新

本次针对容易发生的交付偏差加强规则：

- 开工摘要明确可观察行为、验收和实际写入位置，避免“流程都走了但需求没理解”。
- 新 worktree 不携带未提交改动；不能把路径存在或分支已检出等同于写入所有权。
- 多 agent 使用验收/契约修订号；旧结果重新核对，确认写入停止后才能移交所有权。
- 分开管理测试执行与测试提交，明确忽略规则不作用于已跟踪文件。
- 将验证证据对应到实际代码状态，部分暂存、集成、冲突解决和 hook 改写后按影响重新验证。
- 新增个人约定入口，保持共享规约与个人规则分离；保留“关键歧义才询问”的执行方式。

已完成文档走查、技能结构与引用检查，并在临时本地 Git 仓库复现 worktree、测试忽略和暂存快照三个场景组；这证明 Git 行为和规则针对的问题，不等于 agent 已在真实业务任务中稳定遵循。未修改业务仓库或全局 Git 配置。
