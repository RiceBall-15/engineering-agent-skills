# 多 agent 协作协议

只在已允许委派且确有独立子任务时读取和使用。本文件约束协作方式，不自行授予启用子 agent、创建聊天或发送外部消息的权限。

## 1. 先判断是否值得并行

适合：契约确定后的独立模块实现；不写文件的独立审查；接口稳定后的测试补充；互不依赖的客户端与服务端工作。

不适合：需求尚未澄清；多个任务必须反复改同一核心文件；后一个任务等待前一个的全部结果；一个聚焦索引查询就能完成的源码探索。并行前估算沟通、冲突和合入成本，不能把启动数量当开发进度。

不指定固定模型品牌、型号或角色等级。按用户要求、任务难度和宿主可用能力分配；不自作主张更改已指定的模型。

## 2. 主 agent 的职责

- 保持一份当前任务卡、契约版本和任务板，向所有参与者传递同一份需求事实及明确排除项。
- 先解决接口、状态、数据格式、错误行为等共享契约，再拆实现；不能让不同 agent 各自发明一套协议。
- 指定文件/模块所有权和写入目录，记录依赖、负责人及状态。
- 唯一负责最终整合与任务完成判断。共享文件、依赖清单、锁文件、全局配置、迁移编号由指定负责人处理。
- 发现范围变化立即通知受影响 agent，必要时暂停或取消旧子任务；收回的任务要有明确状态，避免完成后仍继续写入。

任务板可直接写在已有任务记录中：

| 子任务 | 输入/契约版本 | 负责人 | worktree/分支 | 文件边界 | 依赖 | 状态 | 验收证据 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 示例：导入校验 | v1 | agent-a | 独立路径/分支 | parser与对应测试 | 已确定格式 | 待开始 | 待验证 |

建议状态：待开始 → 执行中 → 待审查 → 待集成 → 已验收；另标阻塞/已取消。“代码写完”先进入待审查。

## 3. 分派模板

```text
任务标识、验收修订号与目标：
需求依据和验收行为：
本期不做、用户纠正及禁用的错误技能路径：
代码位置：仓库、worktree绝对路径、分支、基线SHA
输入契约：路径/版本、参数、状态、错误、兼容约束；依赖提交/补丁是否已经到位
允许修改：文件/模块及测试范围；当前项目的测试、夹具与生成物交付规则
禁止修改：共享文件或其他任务范围
允许动作：只读/编辑/本地测试；是否允许提交（推送/合并单独说明）
环境约束：端口、临时目录、测试库、禁止触及的共享环境
依赖任务和交付顺序：
必需验证与完成条件：
遇阻处理：报告证据和最小问题，不自行扩大范围
交接内容：实现摘要、实际文件、提交或补丁、测试、限制、契约变化
```

基线应是明确的功能集成点，不从各 agent 当前目录随意出发。只有在不会重叠写入且宿主支持时，才允许共享目录分工；默认每个可写任务独立 worktree。只读审查可以共享同一份稳定快照。

## 4. 写入和协作规则

- 每次写入都使用分派的绝对路径；禁止子 agent 切换公共主目录的分支。
- 同一文件同一阶段只有一位写入负责人。即使改不同方法也不默认安全；需要共享时先协调所有权或串行处理。
- 需要修改边界外文件或变更契约时，先向主 agent 报告原因和影响。主 agent 更新契约和任务边界后，通知所有消费者。
- 主 agent 不在子 agent 正写的文件中同步修改；接管前先停止写入者并确认最后状态。
- 停止消息发出不等于写入已停止。确认子任务结束/中断状态、待完成命令及最后产物，再转移所有权；无法确认时不启动同一范围的第二位写入者。
- 需求或契约修订后，受影响子任务携带新的修订号继续；迟到结果先标“基于旧版本”，重新核对适用性，不因测试曾通过就直接接收。未受影响任务可继续，不扩大暂停范围。
- 不自行安装依赖、修改全局环境、执行真实迁移、推送/合并或启动递归子任务，除非分派及上层权限明确允许。
- 只读审查输出问题的触发条件、证据位置、影响和修复建议，不未经协调直接改被审查代码。

## 5. 子任务交接模板

```text
状态：待审查 / 阻塞 / 已取消
实现了：对应哪些验收行为
执行位置：worktree、分支、起点SHA、当前HEAD、验收/契约修订号
交付：提交SHA或明确补丁；未提交和未跟踪文件
影响范围：实际修改文件；是否触及共享契约
验证：实际命令、环境、结果与未运行项
风险：已知限制、需要主任务处理的问题
续接：依赖、集成顺序、不能遗漏的配置/迁移
```

不能用“全部完成”替代交接证据。子任务的局部测试不能代表组合后的功能通过。

## 6. 集成顺序

1. 确认子 agent 已停止写入交付内容，取得稳定提交/补丁，保留来源。
2. 检查基线、范围与契约版本，审查差异及必要的周边代码；拒收越界或无关改动。
3. 按依赖顺序在主任务已确认的集成位置整合；不盲目整支合并，也不重复应用同一补丁。
   集成记录注明子任务、源提交/补丁标识及集成后提交/工作区状态；依赖包含未提交改动时先明确传递，不能仅凭相同分支名认定各目录内容一致。
4. 解决冲突时核对双方意图；不能为图省事覆盖其中一方。
5. 按实际边界运行组合验证，例如前后端契约、库与调用者兼容、CLI 输入输出、基础设施配置计划等。各子任务分别通过不代表组合通过；不强制所有项目都采用浏览器端到端测试。
6. 更新任务板和唯一契约文档，检查遗留进程、端口和测试数据。主 agent 给出整体验收结论。

子 agent 超时或失败时先保留其有效产物和未完成状态，再决定续接或重派；不要并发启动第二个写入者去“补上同一块”。
