# 高风险场景与验证

编写测试计划、处理迁移/并发/解析等高风险变更、形成交付结论时读取相关部分。按实际风险选项，不把整张清单强加给所有修改。

## 一、足够的测试由行为决定

| 变更类型 | 最低有意义的验证 |
| --- | --- |
| 纯文案/注释/格式 | 相关渲染或格式检查；确认没有改变行为，不为凑数新增单元测试 |
| 新增/修改业务规则 | 正常路径、边界、失败行为的单元测试；必要的状态与副作用断言 |
| 缺陷修复 | 可稳定复现原问题的回归用例；相关相邻行为；修复前后差异 |
| 前端/客户端交互 | 组件/状态逻辑测试；真实关键交互、加载/空/失败状态；适用的键盘和可访问性验证 |
| API/跨端契约 | 参数和错误协议、身份/权限、序列化、兼容消费者；必要的集成测试 |
| SQL/存储/迁移 | 接近目标引擎的集成验证、样本对账、重复运行、部分失败与恢复 |
| 异步/并发/多实例 | 重复与乱序、竞争、超时、中断恢复、旧执行者晚到写入、资源上限 |
| 性能相关 | 有代表性的规模与基线对照、资源使用和退化条件；不只靠复杂度口头判断 |

如果已有测试确实覆盖新增行为，可补充最小缺口，不要求重复编写同样断言。覆盖率指标按仓库标准执行；没有标准时不编造一个通用百分比。重点说明关键分支及风险是否被覆盖。

测试应断言外部行为、状态或副作用，不只断言 mock 被调用、对象非空或新写函数返回自身生成的预期。协议快照与静态检查可以辅助，但不能代替语义验证。

先运行最接近改动的验证，再运行受影响模块与项目要求的门禁；涉及公共模块时扩大回归。发现历史失败可与原基线对比，不把所有失败默认归为环境。

先确认测试环境与副作用：真实数据库、队列、外部发送、付费 API 和生产配置不能仅因“在跑测试”就视为安全。优先隔离夹具和可控替身；必要的真实集成边界在授权的隔离环境验证。团队的版本控制策略与行为验证要求分别落实，不因交付形式不同而省略关键验证。

## 二、迁移和批量数据变更

先明确：处理对象、环境、租户/资源范围、草稿/在线/历史版本范围、字段映射、冲突策略、执行顺序、权限、失败策略、审计和恢复边界。生成脚本/接口和实际执行刷数分别授权。

适用时采用明确的阶段：

1. **预览**：只读统计与样本差异；说明 dry-run 是否会产生任务记录等副作用，不能把有业务写入的操作称为只读。
2. **提取与备份**：保存源标识、版本/摘要、原字段及映射；不要在提取阶段顺手应用。备份必须早于被覆盖写入，且持久化成功才能继续。
3. **应用**：按确认映射写入，检查源版本未被并发编辑改变；记录成功、跳过、失败及原因。
4. **核验**：比较目标范围、行数、内容/引用与实际读取行为，不能仅看 HTTP 成功或任务不再运行。
5. **恢复**：只恢复迁移所改字段/关联，保留迁移后其他合法修改；必要时使用版本/摘要条件防止覆盖并发编辑。无原始备份时不能承诺精确回滚。

要求由规模和场景决定：

- 提取/应用/恢复各自幂等；重复运行不能覆盖最初备份、重复创建规则或反复破坏引用。
- 指定对象与全量模式共享核心语义。全量模式有明确范围、分批/游标、进度、失败清单和可续接行为；不允许空范围被误解成全部。
- 全量任务要能区分部分成功、失败、取消与成功终态；“任务停止”不是全部成功。
- 跨记录依赖或共享规则变化时，先验证更新顺序与引用完整性；不能只看每条记录独立通过。
- 回滚代码不等于回滚数据。破坏性变更必须说明备份位置、保留期、恢复方式和仍不可恢复的内容。
- 提交前用隔离样本演练：原始状态 → 提取 → 应用 → 重试 → 核验 → 恢复；包含中途失败和应用后正常业务编辑。真实环境执行前确认环境与范围。

## 三、正则与导入导出

涉及正则/表达式时确认使用的引擎与版本、完整匹配还是子串匹配、标志位、Unicode/换行/空字符串、捕获组及替换语义、转义在代码/JSON/数据库中的层数。跨语言或跨存储格式迁移不能只做字符串替换就宣布等价。

用已脱敏真实样本和边界样本做迁移前后对照。外部可控表达式或输入存在时，测试无效表达式、超长输入与灾难性回溯风险；按引擎能力限制资源，不默认假设有超时能力。

导入导出检查：缺失/null/空值/0/false 的区别、类型与精度、重复键或标识、引用重映射、顺序、未知字段、失败是否部分写入及往返等价。业务明确排除的历史对象不擅自纳入修复或拦截范围。

## 四、异步、资源和多实例

先查项目现有执行器、连接池、调度、事务、锁/租约和重试设施；复用合适机制。对本次涉及的风险逐项回答：

- 谁拥有任务？重复触发和跨实例竞争会怎样？结果如何幂等？
- 失败、超时、进程退出后谁恢复？可否安全重试？外部副作用是否会重复？
- 旧执行者晚于新执行者返回时，如何避免覆盖新结果？
- 队列/批次/分页/并发/内存是否有界？大数据输入会不会全量装入内存？
- 远程 I/O 是否长期占用事务或共享资源？权限/配置在异步执行时是否需复核？
- 状态和日志是否足够定位故障？不能记录凭据、完整敏感请求或不必要的个人数据。

这些问题用于发现必须处理的边界，不代表每个项目都需要新造分布式任务系统。

## 五、审查与证据记录

自查或独立审查覆盖：需求符合度、公共契约、相关调用者、错误处理、安全/权限、资源与数据规模、可维护性、缺少的测试、可删除的无关复杂度。必须能指出触发条件与影响，不能只说“建议优化”。

```markdown
| 验收行为/风险 | 实现位置 | 验证入口/命令 | 环境/版本与代码状态 | 结果 | 限制 |
| --- | --- | --- | --- | --- | --- |
| 缺失字段被拒绝 | 实际模块 | 实际测试入口 | 实际提交或 HEAD+相关工作区差异 | 未运行/通过/失败/阻塞 | 明确范围 |
```

结果只使用可证实的状态：通过、失败、未运行、阻塞。保留有用的运行摘要/日志位置及对应提交或工作区状态；不要泄露环境凭据。测试后代码发生变化时说明哪些证据仍有效，重跑受影响部分。

证据描述实际验证对象，不只写“单测通过”。记录关键假设、采用的 mock/真实依赖、相关未提交材料以及测试后有无影响结果的修改。额外验证材料与 CI 覆盖存在差异时明确注明，不用本地结果暗示 CI 已具备相同覆盖。暂存快照与验证对象不一致时，按 Git 细则补验证再形成提交结论。

若无法运行必需测试：完成可运行验证、说明具体阻塞及补跑方式，交付状态标为“待验证”，不宣称需求已全部完成或可安全合并。

## 六、最终完成门槛

- 用户要求的场景有明确行为证据；排除项没有偷偷扩进来。
- 必需单元测试及适用集成检查通过；重要审查问题已解决。
- 需求、代码、测试、契约和必要配置说明一致。
- 分支与暂存区只包含本任务；提交/推送/合并状态真实。
- 剩余风险、未做工作和恢复限制已明确告知；无需变更的领域不添加空洞声明。
