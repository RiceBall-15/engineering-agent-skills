# Git 与 worktree 操作细则

在创建/切换分支、恢复会话、同步、提交、推送、合并或管理 worktree 时读取。本文命令是读取或模板，路径、远端和 ref 必须先由证据确认。

## 一、先读取状态

在已确认的目标路径检查，避免依赖终端上一次所在目录：

```bash
git -C <repo> rev-parse --show-toplevel
git -C <repo> status --short --branch
git -C <repo> branch --show-current
git -C <repo> rev-parse HEAD
git -C <repo> worktree list --porcelain
git -C <repo> branch -vv
git -C <repo> remote -v
git -C <repo> diff --stat
git -C <repo> diff --cached --stat
```

路径和 ref 为占位符，不可原样执行；实际路径需安全引用。远端地址若含凭据，输出给用户前脱敏。`status` 中的未跟踪文件也需检查归属。无分支名可能是 detached HEAD，不能直接当成功能分支使用。

同时读本任务绑定记录。最小记录包含：`task / repository / worktree / branch / base-ref / base-sha / owner / last-verified-head / allowed-integration-direction`。记录不包含令牌、密码等信息。

绑定信息优先保存在宿主可跨轮读取的任务记录/附件中，或团队已有的跨分支可访问位置；不要只藏在当前功能分支中的某个未知文件里。项目内进度文档可链接该记录。若宿主无持久化能力，交付明确的续接卡；不能假称下一轮必然记得。

## 二、选择分支和工作目录

| 观察到的情况 | 操作 |
| --- | --- |
| 同一未完成需求，记录唯一指向功能分支 | 核实后自动继续该分支；不重复询问 |
| 目标分支已被现有 worktree 检出 | 切换执行路径至该 worktree，不在主目录强制 checkout |
| 分支正确且目录无其他写入者 | 使用现有目录，无需再创建 worktree |
| 主目录在无关分支/有其他改动/正被另一任务使用 | 复用或创建隔离 worktree，保留原目录状态 |
| 明确独立新需求，团队采用功能分支且基线已知 | 从确认的基线创建功能分支，记录起点 |
| 团队采用主干开发、发布修复或依赖分支 | 按其既有策略与当前授权执行，记录基线和依赖，不强制改成同一模型 |
| 新需求基线未知、远端默认分支与团队规则矛盾 | 先询问，不从当前分支猜起点 |
| 分支不存在、已合并关闭、身份或改动归属冲突 | 核对记录与历史，确认继续方式后再写入 |

基线依据来自当前明确要求和适用的项目分支策略，远端默认分支可辅助定位，但不自动等于本次发布修复或依赖任务的基线。主干开发也需明确写入归属、并发协调和交付方式；它不自动授权写受保护分支。

网络可用且允许时先 fetch 对应远端引用，记录实际 SHA；fetch 不等于把远端内容合入工作分支。网络失败不能声称基线最新；新需求需要最新主干且无法确认时，询问是否使用已知本地基线。不要用 `pull` 隐式决定合并/变基策略。

确认基线后可按环境选用托管 worktree 工具，或等效 Git 操作：

```bash
git -C <repo> worktree add -b <new-feature-branch> <new-path> <confirmed-base-ref>
```

已有分支且未被其他 worktree 占用时，可用 `git worktree add <new-path> <existing-branch>`。不使用覆盖参数绕过分支占用。共享目录不能在其他写入者工作时切分支。

## 三、worktree 的隔离边界

- worktree 隔离文件检出和暂存区，但共享仓库对象、分支引用等元数据；不把它当成独立 clone。
- 每个工作目录明确拥有者和任务。所有编辑、测试、格式化、提交命令显式使用该目录，避免相对路径写回主目录。
- 新 worktree 从指定提交检出，不携带原目录的未提交改动。依赖这些改动的任务不得假设新目录已经包含它们；先核对差异归属，再按已有授权使用明确提交或经过审查的补丁传递，并验证目标内容。不为搬运擅自提交用户改动，也不复制整棵工作目录。
- worktree 路径存在、分支已被检出，不等于当前任务拥有写入权；结合任务记录和活跃写入者核实。基线、分支或目录在检查后被外部改变时停止相关写入，不能凭旧记录继续。
- 安装依赖前阅读项目初始化方式。环境文件和忽略文件不会自动迁移；只复制确实需要且获准的配置，不把凭据加入版本控制。
- 测试端口、临时目录、数据库/schema、队列、容器和缓存写入空间也要隔离。不同 worktree 连到同一测试数据库，仍会互相污染。
- 不默认共用可写构建目录，不擅自链接依赖目录。只有项目明确支持时复用缓存或只读资源。
- 长任务保存重要的未跟踪文件；清理前检查工作区、未推送提交及所需忽略文件。不能用 `rm -rf` 或强制移除来“整理环境”。托管 worktree 用宿主提供的归档/清理能力。
- 清理只针对本任务创建且已交付/备份的资源，不删除他人的分支或工作目录。归档后更新任务记录。

worktree 的共享元数据、占用限制与管理命令见 [Git 官方说明](https://git-scm.com/docs/git-worktree)。环境与资源隔离是本技能另加的协作要求。

## 四、防止分支混入其他需求

“最初从主干创建”不能证明“现在仍然纯净”。提交和集成前同时看提交历史与文件差异：

```bash
git -C <worktree> log --oneline <confirmed-base-ref>..HEAD
git -C <worktree> diff --stat <confirmed-base-ref>...HEAD
git -C <worktree> diff <confirmed-base-ref>...HEAD
```

记录创建时的基线 SHA，并检查后续 merge/cherry-pick 来源。三点 diff 便于审查功能差异，但不能单独证明没有历史污染；如出现无关需求提交，需要解释其来源和必要性。

- 不引入未经确认的分支历史或无关需求。若项目策略明确要求从集成分支更新、发布修复回合或基于依赖分支开发，则按相应方向、范围和既有授权执行；不能仅凭分支名称判为污染。
- 需要别的需求中的修复时，先明确依赖、最小必要提交及来源，检查是否夹带其他改动；必要时改为独立公共修复。用户未确认跨需求依赖前不引入。
- 允许同步已确认的上游基线时，按项目约定选择 merge/rebase；共享分支重写不能自行决定。同步后重新检查变更范围与测试。
- 发现污染先停止集成并保留证据/备份引用，提出干净基线重建或最小撤销方案。不能自动 reset、force push 来“修好”。有用户授权后才执行具体恢复，并报告协作者如何对齐。

## 五、提交与推送

提交前检查 `diff`、`diff --cached`、`diff --check` 以及必要的暂存区检查；包括未跟踪和忽略文件中是否有必须交付的产物。不要默认 `git add .` 或强制添加被忽略文档；先确认忽略意图。

一个提交包含一个可理解的行为变化及按项目/用户约定允许纳入的测试、契约和说明。测试及生成物的交付范围见下节。无仓库约定时可用：

```text
fix(import): 保留空字段并拒绝不完整记录

原因：旧解析把缺失字段当作空值，导入后无法区分两种输入。
变化：保留原始字段存在性，在写入前校验必填项。
兼容：不修改既有合法记录；错误响应沿用现有协议。
验证：填写实际运行的测试入口和结果，不复制此示例当作证据。
```

提交前已有他人的暂存内容时，不一起提交、不擅自取消暂存；使用隔离工作目录或确认归属后处理。Git 身份缺失时询问，不擅自设置全局姓名/邮箱。

推送需已获授权，并明确本地分支、远端和目标分支。不能因为存在同名远端就猜测推送目标。推送后确认远端分支对应提交；本地提交成功、远端推送成功、目标分支已合并是三件事。

### 按团队策略交付测试与生成物

测试、夹具、快照、生成文件及配置是否入库，读取当前项目规则和 CI 要求，不沿用上一个项目的做法。共享技能不预设其版本控制策略，也不自动将测试目录加入忽略规则。

按明确交付范围精确暂存。忽略规则只影响未跟踪文件的发现/添加，不能作为已跟踪文件已被排除的证明。变更忽略或跟踪策略应有本任务的明确依据；未经授权不退跟踪整目录、不强制添加被排除材料、不撤销他人的暂存内容。

存在经确认的交付例外时，说明验证材料和提交内容的对应关系、复现方式及 CI 限制；具体例外只保存在其适用的任务或项目记录中。

### 已测试的内容必须对应待提交内容

检查暂存差异时同时核对同文件的未暂存变化、相关未跟踪/忽略依赖及测试后的编辑。工作区测试通过不能证明部分暂存版本也通过；例如工作区有两个相互依赖的修复，暂存区只选其一。

能明确确认行为与依赖一致时沿用已有证据；不一致或无法确定时，在隔离目录还原待提交快照并运行相关验证，或重新整理暂存范围后验证。不得通过在共享目录 stash/reset 来制造“干净测试环境”。额外本地验证材料按已确认的交付范围处理，不混入待提交快照。

提交前最后检查 HEAD 与暂存区未被其他写入者改变；提交后核对提交内容，hook 若自动改写代码则评估影响并补跑相关验证。未获授权不能关闭 hook 或绕过门禁。

## 六、按项目策略执行集成

1. 确认源 ref → 目标 ref、两边最新状态、团队集成方式及已有授权。
2. 在目标所属工作目录或经确认的集成目录执行；目标目录有其他改动或写入者时先隔离/协调，不能切换别人的活动目录。
3. 遵循项目的 PR/CI/merge/rebase/squash 方式，不绕过保护规则；这些是可选策略，不要求全部执行。
4. 冲突逐项核对双方意图，不能全部 ours/theirs 盲选。业务含义不明时仅暂停相关冲突处理并澄清。
5. 验证集成结果；已授权推送时明确目标并核对远端。
6. 后续回到仍有效的本任务目录。是否还需从目标同步到源、将修复回合其他维护分支，取决于项目策略和相应授权；不由刚完成的一次合并自动推断，也不一律禁止。

分支包含未确认的无关改动时先处理，不直接集成。已确认的依赖提交或团队要求的同步不应被误判为污染。

`git merge` 将指定历史合入当前分支，其方向由当前检出的目标决定，参见 [Git 官方说明](https://git-scm.com/docs/git-merge)。执行前核对目标工作目录，不能只核对命令中的源分支名。
