# 需求输入与项目上下文

在首次接手、需求复杂、用户纠正方向或上下文续接时读取。先获取事实再提问；无需每轮重填全部内容。

## 最小任务卡

```markdown
任务：<可识别的需求名称/编号>
验收修订：<例如 r1；需求/契约变化后更新，并说明哪些旧决定失效>
阶段：<评审 / 方案 / 实现 / 修复 / 交付>
目标：<谁在什么情况下获得什么可观察结果>
依据：<适用的用户确认、Issue、协议、需求/设计版本或错误复现；注明冲突/过时材料>
本期做：<边界>
本期不做：<明确排除项>
验收：<输入/前置条件 → 动作 → 结果，含重要反例>
现状与复用：<真实入口、模块、组件、工具、表、已安装依赖及限制>
变更影响：<接口/消费者/持久化/配置/权限/发布顺序>
执行位置：<仓库根目录、worktree绝对路径、任务分支、基线ref与SHA>
已确认决策：<内容、依据、作用范围>
待确认：<只列会影响正确性、兼容性或授权的关键问题>
验证：<命令/测试入口、关键行为、环境依赖>
测试交付：<当前模块的测试/夹具/生成物入库与 CI 规则；任务例外仅在明确存在时填写>
允许动作：<已授权的提交/推送/合并方向或环境操作>
进度：<完成、未完成、阻塞、下一步>
```

低风险例子可以缩为：“修复空搜索结果的提示；复用现有 EmptyState；在本任务分支修改列表组件；验证空结果与正常结果两种状态。”不要为一行文案另起十份文档。

## 用户可直接提供的开发提示

以下是可选输入模板，未知字段可留空，agent 自行从项目中补齐可查信息。

```text
请按 development-lifecycle 处理下面的需求。

我要解决的问题：
用户操作和预期结果：
需求文档/原型/错误示例：
本期不做：
已有分支/相关需求：
必须遵守的规范或兼容要求：
如何算做完：
可以执行的动作和环境：

先检查仓库、会话分支、已有实现和依赖；普通细节自行判断，关键歧义再问。
```

## 怎么判断必须问

| 缺口 | 可以自行补齐 | 必须澄清的情形 |
| --- | --- | --- |
| 目标行为 | 已确认需求或协议已有明确示例 | 有效材料相互矛盾；“全部”究竟包含哪些对象/版本不明 |
| 任务归属 | 当前会话记录唯一对应的分支与worktree | “新需求”与“继续旧需求”都解释得通；多个分支都可能对应 |
| 实现细节 | 同模块命名、标准组件、格式 | 决定前后端职责、改变公共协议或需新增外部服务 |
| 权限 | 已确认角色矩阵和既有鉴权链 | 谁能读取敏感字段、谁能触发全量操作不清楚 |
| 迁移 | 已定义映射和样本 | 覆盖旧数据、历史版本范围、丢字段或无法精确恢复 |
| 交付 | 已授权目标分支的提交/推送 | 生产执行、未知远端、共享历史改写、合并方向不清 |

好问题示例：“‘迁移全部’是否包括已发布历史版本？这会影响备份量和回滚范围。现有需求只明确草稿与在线版，我建议先限制为两者；请确认是否包含历史版本。”

差问题示例：“还有别的要求吗？”、“所有操作是否都可以？”、“要不要最佳实践？”这些问题不能决定具体实现。

## 新项目接手建议

先看是否已经具备索引和架构文档。缺少时可以合并成一次可选提问：“是否补充适配当前语言的代码索引（例如 CodeGraph），以及整理一份轻量架构说明？两项可分别选择，也可以先做本次需求。”记住用户选择，仅在条件变化时再次询问。

若用户同意安装索引：先确认工具对当前语言的支持、项目既有同类能力、访问权限、官方使用方法、项目范围和生成文件位置；不要凭记忆执行陌生安装命令。安装、初始化、重建是不同动作，按实际缺口执行。项目已有明确初始化命令时沿用；未授权不改全局环境。

使用索引时：

- 符号定义/签名、调用者、影响面、完整调用路径用对应结构工具。
- 架构问题先取聚焦上下文，再一次批量读取相关源码；链路问题优先完整路径查询。
- 字符串、注释、日志、配置值用文本搜索；没有可用索引时才回退到文件阅读和原生搜索。
- 遵守项目对索引工具的更具体规定，不对可靠结果重复检索。刚编辑后的索引可能短暂滞后；只有已观察到路径或版本不一致才诊断，不把每次命中都当成可疑。

## 架构说明应回答什么

采用已有文档入口；没有时可建议 `docs/architecture.md`。以本次实际读到的代码为边界，不把未调研内容写成确定事实。

1. 业务能力：用户是谁、完成哪些核心任务、主要对象及生命周期。
2. 系统边界：前端/服务/客户端/外部依赖各自承担什么。
3. 模块索引：能力 → 入口 → 核心模块 → 测试，优先路径与符号，不复制整段源码。
4. 关键链路：请求/事件如何经过权限、处理、存储和返回；按需画简图。
5. 复用目录：公共组件、资源池、执行器、鉴权、日志、加密、导入导出等已存在能力及限制。
6. 开发入口：受支持的运行时范围、构建/测试/本地启动方式、所需依赖。不把某台电脑的精确版本误写成全员要求。
7. 已知限制与证据：本次核对的版本/日期、尚未确认项。

只在结构变化时更新相关部分，不把架构文档写成每日流水账。

## 没有开发规约时

检查适用的规则文件、格式/静态检查配置、构建和测试配置，再选 2–3 个邻近且仍在维护的同类实现作为样本。记录本次采用的惯例及样本位置；有明确团队工具配置时优先采用它。

需要抽取的项目：命名和目录、模块边界、接口与错误形式、空值/可选值处理、日志脱敏、异步方式、依赖注入或资源生命周期、注释语言与深度、测试夹具、提交风格。

遵循惯例不代表复制漏洞、吞错、泄露信息或越权行为。若修正会扩大本任务范围，明确问题与最小处置选项，不暗中重构全仓。

## 技能误路由的防复发方式

维护明确的“动作 / 对象 / 适用技能 / 排除项”。假设某技能只用于读取设计资源，那么请求提及相同产品名并不意味着它适用于修改业务代码；应按其真实能力及明确边界判断，不从名称推导权限。

用户纠正后执行四步：停止错误技能后续动作；核对它是否已造成文件或外部状态变化；把规则按项目/用户全局范围持久化到可用规则入口；续接和再分派时带上该边界。只说“记住了”不构成持久化。

## 需求变化后的处理

先区分新需求、对原需求的澄清、对已实现行为的否定。按验收项列出“保留 / 修改 / 移除 / 待确认”，停止失效的子任务，更新方案与契约，再继续依赖它的开发。不因用户一句“继续”重新启用已经否决的方向。

用户询问原理、要求进度或补充限制，通常是当前任务中的插入信息，不自动取消原目标。先回答并更新相关约束，再继续仍然有效的工作。跨轮记录区分“已确认事实”“待验证假设”“已废弃决策”，避免把旧猜测提升成事实。
