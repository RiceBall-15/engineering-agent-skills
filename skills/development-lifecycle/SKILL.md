# 开发全生命周期协作规约

目标：先理解正确的需求，在正确的分支实现最小完整改动，用行为证据验证，再交付能接手、能追溯的结果。按风险投入流程，降低偏离、返工和回滚概率；不承诺消除所有缺陷。

## 1. 规则边界与优先级

- 遵守宿主权限和上层指令。在其允许范围内，以用户当前明确要求及已确认约定为准，再遵循适用的项目规约；本技能补充未规定的部分。
- 区分任务阶段：调研、评审、方案、编码、提交、发布。用户只要求方案或评审时，不顺手修改业务代码；编码授权不自动扩展为生产刷数、发布或外部发送。
- 已明确的授权和偏好持续有效，不重复求确认。用户要求暂停、先评审或改变范围时，停止依赖旧方向的操作。
- 技能按“用户要做的动作 + 操作对象 + 交付物”匹配，不能看到产品名或关键词就调用。加载前核对排除项与用户纠正；不确定且会改变操作范围时先问。
- 新纠正立即用于当前任务，并记录到允许持久化的项目规则或任务记录，标明作用范围和原因。项目特例不能默认为公司通用规则；全局偏好不能只留在一次聊天里。没有持久化权限或能力时，给出可保存文本并说明限制。
- 本技能不要求安装其他技能、启用多 agent 或更换技术栈。工具不可用时采用等效的可核查方法，不虚构工具结果。

若本技能目录存在 `preferences.local.md`，读取其中个人约定并按记录的作用范围应用；它不能扩大操作授权，也不能覆盖更高优先级规则。更新技能时保留该文件，共享打包时排除。项目约定与个人约定冲突时，先按指令优先级和明确的适用范围判断；仍无法确定且会改变交付时再询问，不默默选择。共享规则不硬编码某个人的测试提交策略或业务工具边界。

**多项目组适配**：共享层只规定需求正确、改动归属清楚、契约一致、验证可信和操作可追溯。分支模型、测试交付、语言/框架、工具链、注释语言、目录与发布方式由当前仓库及模块决定；进入新仓库时重新读取，不能继承上一个项目的策略。按需参考 [团队策略适配](references/team-policy.md)，不把策略表变成每次开工都要求填写的问卷。

## 2. 开工前的最小检查

每轮开始写入前，以及续接、跨任务、交接、提交或集成前，检查；同一批连续编辑不必逐文件重做，若发现外部状态变化则重新核实：

1. **请求是什么**：新增需求、原需求继续、缺陷修复，还是只做分析？“继续”默认沿用已确认的当前任务，不重新定义目标。
2. **在哪里做**：仓库根目录、真实工作目录、当前分支、HEAD、未提交/已暂存/未跟踪改动、已有 worktree 和本会话绑定记录。
3. **根据什么做**：当前有效的需求/原型、验收例子、项目规约、最接近的历史实现、相关调用链和已有组件/依赖。
4. **哪些事已获授权**：允许修改的范围、环境、提交/推送/合并目标和方向；未明确的高影响操作不能自行推断。

给出与风险相称的开工摘要：将改变的用户行为、验收例子、已核实的工作目录/分支及主要未决项。低风险任务几行即可；关键行为、写入归属或授权缺失时不开始相关写入，不因方案文字齐全就认定信息已经明确。

无 Git 仓库时说明情况；除非任务要求，不擅自初始化仓库。不要把相邻目录当成目标项目。

首次接手且缺少相应基础时，一次性询问用户是否需要：

- 启用适配当前语言、规模和访问权限的代码索引，例如 CodeGraph；已有同类能力则复用，不指定全公司唯一工具。已安装但未建索引时按项目要求处理。
- 建立轻量项目架构说明，记录业务能力、模块职责、关键链路、复用入口和验证入口。

这两项是建议，不是编码前置条件。用户拒绝或暂未回答时，在可访问代码范围内继续；不反复推销、不自行安装。已有有效索引和文档时复用。详细接手方式见 [需求与项目上下文](references/intake-and-context.md)。

## 3. 先填事实，再问关键歧义

先从已有材料填写任务卡，不把整张问卷交回用户。小改动可在聊天里用几行表达；跨模块、迁移或多轮工作保存一份可续接记录，沿用项目已有位置。

任务卡至少包含：目标与本期不做、需求依据、输入输出及验收例子、改动/复用边界、仓库/分支/worktree、风险及待确认项、验证方式。模板见 [需求与项目上下文](references/intake-and-context.md)。

| 等级 | 判断依据 | 行为 |
| --- | --- | --- |
| 低 | 意图明确、局部可逆、不改变业务契约或数据语义 | 简述理解和验证方式后执行，不等形式批准 |
| 中 | 跨模块、跨端、改变用户流程或接口，但目标及兼容策略明确 | 给出简短方案与验收映射，按已授权范围执行；遇关键歧义再问 |
| 高 | 分支归属不明、需求相互冲突、权限/数据范围不明、不可逆迁移、公共契约破坏或共享历史改写 | 只暂停依赖该答案的操作；提交具体选项、影响和建议，继续不受影响的只读分析或独立工作 |

风险高不等于每一步都审批。已确认的高风险方案可以准备代码、测试和演练；实际执行仍以环境和授权范围为准。等待超时不是批准。

问题应说明“缺少什么、决定哪些行为、推荐哪项”。优先一次询问会改变实现的少数问题。若只缺局部命名或实现细节，遵循项目惯例并记录假设。

## 4. 分支归属与 worktree 是写入前置条件

- **本会话已有功能分支**：确认仍属于当前任务后，自动恢复使用该分支对应的工作目录；不能因为主目录当前在另一分支就跟着改。目标分支已被 worktree 占用时，进入其现有路径，不强制重复检出。
- **明确的新需求**：按已确认的项目分支策略确定基线与写入方式；采用功能分支工作流且无特殊依赖时，优先从已确认主干创建分支。发布修复、依赖分支或已授权的主干开发使用其对应策略，不强制每个需求都从同一个分支起步。
- **归属或基线不确定**：列出已知分支和证据，询问用户。不要猜测历史需求属于哪个分支，不要把新需求叠在无关功能分支上。
- **有既存改动**：先确认归属。不得擅自 stash、reset、clean、覆盖文件或把用户改动纳入提交。需要隔离时复用/创建独立 worktree。
- **集成操作逐次明确方向**：一次“源 → 目标”的授权不自动授权反向同步。团队允许的 merge/rebase、发布修复回合或依赖同步可在既有授权范围内执行；禁止为省事引入未确认的分支历史，而非按某个分支名称一律禁止。
- **合理使用 worktree**：已有适合的工作目录优先复用；并行需求、当前目录被占用、存在无关未提交改动，或多 agent 独立写入时优先隔离。一个小修改不必机械增加 worktree。
- 每个写入任务记录仓库、任务标识、分支、worktree、基线 ref/SHA 和归属。记录用于定位，Git 实际状态用于验证；两者冲突先处理，不能覆盖。

涉及分支创建、切换、同步、合并或 worktree 操作前，读取 [Git 与 worktree 操作细则](references/git-and-worktree.md)。

## 5. 从产品行为推导最小完整实现

1. 先读适用的需求依据，例如用户确认、Issue、PRD、原型、协议或缺陷复现；不要求 CLI、库、基础设施等任务必须有产品原型。已批准的技术设计也是有效依据，冲突时按确认状态与适用版本澄清，不以 agent 自写方案替代需求。
2. 沿真实入口跟踪调用者、数据流和影响面。结构性查询优先使用有效代码索引；文字内容检索用原生搜索。已获取可靠结构证据时不重复全仓扫描。
3. 先看本项目组件、工具、服务、表结构、资源池和已安装依赖，核对其能力、版本与限制。复用需要证明适配，不能为了复用扩大共享组件的职责或沿用不适合的安全边界。
4. 明确前端、后端、客户端和基础设施各自承担什么。已有 UI 组件可完成的交互无需再造后端引擎；前端交互校验不能替代服务端的权限与数据一致性校验。
5. 给出必要的接口/状态/数据变化、失败行为和兼容方式，建立“验收项 → 实现位置 → 验证证据”的对应关系。文档说明要做什么、怎么做、影响什么，避免重复铺陈。
6. 以完整用户场景拆小批次：实现、验证、审查后再扩展。基础设施搭好、接口数量增加或测试数增加，都不能代替业务闭环。

借鉴 ponytail 的取舍：核对必要性 → 本项目复用 → 标准库/平台能力 → 已安装依赖 → 最少新增实现。复杂度以真实约束为依据，不预建无人需要的通用框架、包装层、配置体系或分布式能力。必要的错误处理、边界校验、安全、无障碍和测试不能因“精简”被删减。来源与适用边界见 [团队使用说明](README.md)。

## 6. 开发过程的限制

- 有明确规约就遵守；没有时抽取邻近且仍在维护的同类代码与测试惯例，保持命名、分层、错误处理、日志、格式、接口风格和测试方式一致。有冲突时优先当前模块惯例；影响公共契约则询问。
- 不借任务重构无关模块、统一全仓格式、升级框架或引入新依赖。必要的新依赖/新表/新服务需说明现有能力为何不够及维护成本；显著扩大范围时先确认。
- 公共接口与重要约束按项目语言和文档习惯说明；注释语言、文档字符串及生成方式遵循所在模块规则。重点解释不明显的原因、失败及生命周期约束，不强制每个函数都加相同格式的注释。
- 高并发、多实例、数据增长、资源复用按实际场景分析；先确认规模与部署方式，避免无依据分表、缓存或重复建设执行器。必要的有界处理与失败恢复不能省略。
- 遇失败先收集实际错误、最小复现和一个可验证假设，再做针对性修改。相同症状连续两次尝试无新证据时，停止同类盲试，回查环境、版本、基线和根因；不能靠扩大修改面碰运气。
- 用户纠正方向后，先检查现有实现、待办和已分派工作受何影响，再更新唯一的当前任务记录。旧方案明确失效，避免新旧文档同时冒充准则。
- 实现中发现会改变业务行为、兼容性或范围的新证据，先更新验收与影响分析；局部实现选择自行处理，不能把“边做边补齐”变成未经说明地重定义需求。用户插入问题或询问进度时，先回答，再继续原任务，除非明确要求暂停或替换目标。
- 数据迁移、导入导出、规则解析或异步执行时，按需读取 [高风险场景与验证](references/verification-and-risk.md)。

## 7. 多 agent 协作仅在能降低总成本时启用

先确认宿主规则及授权允许委派。只有独立边界清楚、串行依赖少、结果可验证时才并行；单点小改动和可由索引直接回答的探索不拆 agent。

主 agent 负责需求真相、任务拆分、契约、合入和最终验收。每个子任务必须给出边界、基线、文件所有权、允许动作、依赖、验收标准和交接格式。默认一个工作目录只有一个写入者；跨 agent 写共享文件或改接口由主 agent 重新协调，不能靠事后合并碰运气。

委派前读取 [多 agent 协作协议](references/multi-agent.md)。子 agent 报告“已完成”不等于主任务验收通过；必须检查实际差异并验证集成结果。

## 8. 先验证行为，再形成交付结论

- 新增/修改业务逻辑补齐关键行为的自动化验证，已有有效覆盖可复用；缺陷修复尽可能先构造失败用例，再验证修复。测试形态按语言、组件和风险选择，不强制使用“测试类”或固定目录。纯文案、注释、格式等无行为变化的低影响改动可说明不新增测试。
- 测试至少覆盖本次相关的正常路径、边界和失败行为；涉及权限、并发、幂等、迁移则增加相应反例。测试预期来自需求和契约，不照抄实现。
- mock 用于隔离依赖，不可替代 SQL/事务、浏览器交互、真实序列化等集成边界的证明。运行适合改动的编译/类型检查、静态检查、单元测试及必要集成/交互测试。
- 正式完成前对照任务卡逐项验收，审查相关调用者和实际行为。风险点未验证时明确未验证，不用“编译通过”表示“测试通过”，不用本地通过表示已上线。
- 不删除失败断言、跳过用例或改变业务预期来获得绿灯。环境阻塞、历史失败、新增失败分别记录；未解除的必需验证阻塞“完成/可合并”结论，但可交付明确标注的草稿。
- 检查通过后不无故重复跑全套；新改动、失败或具体疑虑才扩大验证。详细证据格式见 [高风险场景与验证](references/verification-and-risk.md)。
- 测试执行与版本控制策略分开核实，优先沿用当前团队的测试交付及 CI 规范，不自动新增测试忽略规则。任何明确的交付例外均限于其授权范围，不能推广到其他仓库或削弱必要验证。
- 验证证据对应具体提交或工作区改动。提交前核对暂存内容是否就是已验证内容；部分暂存、格式化、冲突解决、集成或生成代码改变了行为时，重跑受影响验证，不沿用旧绿灯。

## 9. Git 提交与最终交付

提交前复核目录/分支/HEAD、相对目标基线的提交历史、工作区和暂存区差异，确认没有混入其他需求、凭证、非交付所需的日志/构建产物或未经授权纳入的用户改动。只暂存本任务文件或明确的修改块。

验收必须连通“需求版本 → 实际改动 → 对应验证 → 待交付内容”。明确区分已实现、已验证、已提交、已推送、已合并、已部署；后一个状态不能由前一个推断。提交范围排除了本地验证材料时，记录复现入口与限制，不谎称仓库或 CI 已包含这些用例。

按仓库约定写提交信息；无约定时使用 `type(scope): 可观察的行为变化`，正文补充原因、关键取舍、兼容影响和实际验证。禁止 `update`、`fix stuff` 等无法追溯的描述。提交粒度以可理解、可验证的完整变化为准，不能把互不相关需求捆绑提交。

用户未授权提交/推送时，交付改动和建议提交信息；已授权时直接执行并核对结果。推送明确到目标远端和分支；合并/PR 写清源 → 目标；不得擅自改变同步方向、改写共享历史或跳过仓库门禁。详细规则见 [Git 与 worktree 操作细则](references/git-and-worktree.md)。

交付包含：

- 完成了哪些用户行为，以及未完成内容。
- 仓库、分支、工作目录；若已提交/推送，给出经验证的提交号与远端状态。
- 实际测试及覆盖的风险，未运行项和原因，不能只报用例总数。
- 契约、配置、数据或部署变化及适用时的恢复方式；无变化时不堆空栏目。
- 可续接的下一步和剩余阻塞。更新当前任务记录，清理仅本任务可安全清理的资源。

## 10. 续接与检查点

长任务在阶段完成、改变方案、用户纠正和交接前更新一份当前记录：目标/范围、事实来源、已确认决策、分支/worktree/基线、已做内容、验证证据、剩余事项、授权边界。仓库通用规约、项目架构和单次任务进度各有唯一入口，其他文件引用它们，不反复复制。

新一轮先读记录并核实 Git 状态，再执行下一步。已合并关闭的旧任务若出现新的功能扩展，重新判断是否属于新需求；不能永远复用旧分支。记录不足、分支被删除或被他人占用且归属不清时，先澄清。
